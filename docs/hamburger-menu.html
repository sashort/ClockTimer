<hamburger-menu>

Reusable anchored hamburger menu custom element. It owns popover placement, horizontal paging, parent-menu promotion, directional animation, safe-boundary geometry, and promoted-menu scrolling. Application-specific commands and visual styling stay outside the component.

WMOF integration: the main UI uses this custom element with safe-boundary="#speechMicBar". The same element is intended for reuse in unrelated projects.

Core behavior

Invisible opening calculation

Immediately before the popover opens, the component renders it invisibly and measures the current visible menu content. It partitions rows into panes, measures the finished panes again, and records the tallest pane height. Once the popover enters the top layer, it reconciles placement and freezes that measured height before revealing the menu. The hamburger itself never moves.

Natural pane height

The initial pane starts at the height required by its contents, or at the common height of the tallest horizontal pane when paging is needed. The safe boundary is a maximum constraint; it is not the pane's default height.

Anchor positioning

The trigger is a CSS anchor. The popover uses position-try fallbacks to find a valid location above, below, left, or right of the hamburger.

Horizontal paging

Normal content never vertically scrolls. If it is too tall, the element packs top-level rows into horizontally swipeable panes. Every normal pane uses the height of the tallest pane in that layout.

Parent promotion

Opening any parent promotes it. Promotion is structural behavior, not an overflow fallback. Nested parents create a promotion stack.

Frozen transition pane

The pane freezes its measured base width and height during the invisible opening calculation, before the hamburger is revealed. Promotion DOM changes cannot resize that pane, but the lock remains externally responsive: viewport resize, live safe-boundary motion, and observer-driven layout constraints can re-clamp the frozen dimensions in place. The current locked height is exposed through --hamburger-menu-frozen-pane-height; when observers retarget it mid-transition, the pane interpolates to the new height instead of snapping. The same lock is retained for the entire open hamburger session and is released only when the hamburger closes.

Live DOM and size response

MutationObserver and ResizeObserver feed one coalesced layout pass. Added, removed, moved, hidden, resized, and text-changed menu content is remeasured automatically; direct children added to <hamburger-menu> are adopted into the internal source. Resize targets are diffed instead of repeatedly disconnected/re-observed, avoiding observer feedback loops.

Immutable hamburger anchor

The trigger is never translated to make the popover fit. Safe-region corrections are applied to the popover, preserving the hamburger's document position.

If the trigger does not already have slot="trigger", the element uses its first direct child button and assigns the slot automatically.

Safe boundary

The safe boundary is a maximum available height constraint; it never becomes the pane's starting height. On open, pane height is measured from its contents (or the tallest generated panel) and is only clamped if that natural height exceeds the safe region.

safe-boundary accepts a document selector. The resolved element must generate a usable block-level box such as block, flex, grid, flow-root, table, or list-item. Inline boxes, display: contents, hidden elements, table-internal boxes, and zero-size boxes are rejected. If the explicit boundary is invalid, the component falls back to automatic boundary discovery and finally the usable document edge. While the menu is open, the component samples the accepted boundary's live getBoundingClientRect() each animation frame, so CSS transforms and animations that move the boundary without resizing it still update pane limits.

Margin rule

When a safe boundary exists, the external gap is calculated from the hamburger-menu element's margin plus the safe-boundary element's margin. The margin of the last menu item is not separately added to the boundary calculation. The resulting safe region is always clamped to the usable document/viewport edge, including document and body bottom margin and padding. If an animated boundary reaches that usable edge, panes stop there rather than extending past it.

No explicit safe boundary

If safe-boundary is omitted or cannot be resolved, the component first tries to discover a useful boundary. It prefers elements explicitly marked with data-hamburger-safe-boundary, then nearby semantic toolbar/status/footer elements and visible fixed or sticky layout elements. If no suitable boundary is found, the component falls back to the usable document/viewport edge, accounting for document and body bottom margin and padding.

Positioning and position-try

The popover starts below the trigger and exposes multiple @position-try alternatives. The browser may place it:

  • below-start,
  • above-start,
  • below-end,
  • above-end,
  • to the right, or
  • to the left.

The final popover receives data-placement="above|below|left|right". Projects can use this to orient arrows or other decoration.

.my-menu > .hamburger-menu-popover[data-placement="above"]::after {
    /* point the callout arrow down toward the trigger */
}

Application-selected primary position

The reusable element does not force one application layout. A project should choose its preferred position-area in its own stylesheet; the component's position-try options remain available as fallbacks.

/* WMOF: below the hamburger, with the pane's left edge aligned from the anchor side. */
.main-menu > .hamburger-menu-popover {
    position-area: bottom span-right;
    inset: auto;
    align-self: start;
    justify-self: start;
}

Opening lifecycle

  1. The popover is marked as calculating and rendered at opacity: 0.
  2. The component measures the safe region and the visible top-level rows.
  3. Rows are packed into horizontal panes. If multiple panes are required, every pane is assigned the height of the tallest packed pane.
  4. The browser's anchor-positioning / position-try result is reconciled against the safe region. Any correction moves the popover, never the hamburger.
  5. After a second frame confirms placement, the popover is revealed at opacity: 1.

This prevents the user from seeing temporary measurement geometry.

Applications should also cloak pre-upgrade light-DOM menu rows so they cannot flash before the custom-element script runs. WMOF marks the button with slot="trigger" in static HTML and hides the other direct children while hamburger-menu:not(:defined).

Promotion model

Opening a parent

Primary promotion starts with the pane's menu items visible. An inherited, registered CSS position property on the active panel animates the selected parent. Coverage measurements enumerate visible leaf submenu items through the second menu nesting level; their rendered bounds affect the calculated keyframe percentages. Sibling groups that own child menus are not animated or hidden. A temporary keyframe changes each affected item's opacity to zero when the selected parent covers it, keeping the pane layout stable during motion; nested leaf items then become display: none when the motion ends. Deeper menu items and decorative markup are not animated as separate rows. There is no overlay mask. Promotion of a child within an already promoted parent follows its separate nested motion path.

  1. The pane is already frozen from hamburger open; nested promotion does not create or replace the lock.
  2. Measure the nested parent's current rectangle and its promoted rectangle at the hamburger-side edge of the focus layer.
  3. Insert a placeholder in the nested parent's original slot, then move only that nested parent into the focus layer.
  4. Animate the nested parent's x/y position and width/height from its original bounds to its promoted bounds. The previous parent translates only on the y axis; its x position stays fixed.
  5. Hide the previous parent once the nested parent reaches its destination.
  6. Pause for 75 ms, then open the nested parent's children inside the still-frozen pane.

Closing a promoted parent

Visible submenu borders on the left are recorded when children open and restored before their collapse animation begins. Returning from primary promotion restores affected leaf items' display before running their saved opacity keyframes in reverse. Sibling groups with child menus remain untouched. Temporary keyframes and CSS threshold values are removed after the animation.

  1. Collapse the promoted parent's children completely while the pane remains frozen, then wait the same 75 ms boundary pause.
  2. Show the previous parent and measure the placeholder that marks the nested parent's original slot.
  3. Animate the nested parent's x/y position and width/height back to that slot while the previous parent translates only on the y axis.
  4. Move the nested parent back into its original DOM slot and remove the placeholder and animation state.

Terminology: in this component, a pane is the visible horizontal menu page / promoted viewport whose dimensions are frozen during transition mechanics. A parent menu is the group being promoted inside that pane.

Promoted scrolling

A normal pane never scrolls vertically. Vertical scrolling is enabled only when the currently promoted parent and its opened children are taller than the available safe region.

Paging

Top-level content is first measured in one unconstrained column, then packed into panes according to available height. After partitioning, the rendered pane heights are measured again and the tallest becomes the common height. Horizontal scrolling uses scroll snap and works with touch/pointer swipes. A position indicator tracks fractional scroll progress. The safe boundary only caps the measured height.

</hamburger-menu>

WMOF keeps Speech's crane/scaffolding animation outside the custom element and listens to parentopening/parentclosing. This is intentional: the reusable element owns navigation mechanics, while applications own semantic effects.

Design rules for reusable menus

  • Use a wrapper around every parent button and its controlled submenu.
  • The parent button must reference the submenu with aria-controls.
  • The submenu should start with hidden and the button with aria-expanded="false".
  • Do not implement a second click handler that manually toggles hidden; let <hamburger-menu> own parent expansion.
  • Application code may freely add, remove, move, hide, resize, or change text in menu rows. Mutation and size observers schedule a coalesced repack automatically.
  • Direct children appended to <hamburger-menu> after connection are automatically adopted into the internal menu source.
  • Use data-hamburger-safe-boundary on a preferred discoverable boundary when you do not want to hard-code a safe-boundary selector.
  • refresh() remains available for unusual external geometry changes that do not produce resize, scroll, or DOM mutation signals.

Reduced motion and accessibility

The base stylesheet disables structural transitions when prefers-reduced-motion: reduce is active. The trigger receives aria-haspopup="menu" and an updated aria-expanded. Parent buttons retain their existing aria-controls and aria-expanded semantics.
